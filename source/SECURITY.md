# Security and trust boundaries

Lateef gives the MCP client real read/write access to explicitly controlled browser tabs. Pair only with clients you trust. Browser page text is untrusted data; an AI client must not follow instructions embedded in web pages as if they were user instructions.

The broker binds only to `127.0.0.1`, validates the Host header, rejects ordinary web origins, requires a private local admin token for MCP-side RPC, and authenticates extension WebSockets with a profile token. The token is never placed in a URL. Initial extension enrollment requires a single-use 96-bit pairing code with a two-minute expiry. The broker stores the extension token's SHA-256 hash, not the raw value.

The admin token is in the user's private state file, and the extension token is in Chrome extension-local storage. Other programs running as that same OS user may be able to access those secrets; this is not a sandbox against a compromised user account. File modes are best-effort platform permissions, not an encryption layer. Loopback traffic is local HTTP/WebSocket, not TLS.

Full control is a separate build (`lateef extension --full`) that adds Chrome's `debugger` permission; the standard extension and the store listing do not have it. With it switched on in the popup, an agent can see a controlled tab as an image, send trusted mouse and keyboard input to it, run JavaScript in it, and read its console messages and request URLs. That is close to everything the person could do in that tab, so switch it on only for clients and tasks you trust, and switch it off afterwards. Password fields are still refused for typing, but a script run in the page is not similarly limited. The debugger is attached per controlled tab on first use and detached when the session ends or the switch goes off.

While an agent controls a tab, the extension adds one marker element to that page (a status chip and a flag in a closed shadow root, attached outside `<body>`). It reads nothing from the page, takes no clicks, listens only for mouse position so the chip can move out of the way, and is left out of snapshots, but a page's own scripts can observe that the element exists, so a site can tell Lateef is in use on that tab. The popup switch removes the page markers and the tab group. DOM tools require session ownership and a currently selected window. A guessed tab ID grants no access. User-shared tabs cannot be closed by an agent. The extension has no content script, screenshot tool, desktop input, debugger permission, remote analytics, remote control server, provider API, or model invocation. It requests broad HTTP(S) host permissions so it can access agent-created tabs; those permissions are more extensive than a per-site allowlist. A per-site grant UI is a future hardening item.

Tabs opened by a session that ended without closing them (its process was killed, or a tab kept unsaved changes) stay open as orphans in the paired window. Any connected session can list and adopt them, just as any session can open tabs in that window. Tabs the person shared are never orphaned: they are released when the session ends. Timeouts are ambiguous: an action may have run even if the result was lost. Mutations are never automatically retried. Reconnection does not authorize switching to another paired profile, window, or session.

The extension and the broker prove the pairing to each other. Each answers the other's fresh random challenge with an HMAC keyed by the SHA-256 of the pairing token, so the token is not sent after pairing, and the extension runs no command until the broker has proved itself. When pairing, the broker first proves it issued the pending code (an HMAC keyed by the code's hash), and only then does the extension send the code. A local program that takes the broker's port while the broker is not running learns neither the token nor the code. Extensions older than 0.2.0-beta.6 still send the token, and the broker still accepts them.

This is an early prototype. Do not treat initial tests as an audit or a guarantee for sensitive workflows. Report vulnerabilities privately at https://github.com/DKKowalski/Lateef/security/advisories/new. Do not publish sensitive exploit details in a public issue; do not include pairing codes, tokens, browser data, or authentication cookies in public reports.

Uploads: the AI client chooses the local file paths for `browser_upload`, so a manipulated client could try to attach sensitive files. Paths are resolved through symlinks and, by default, any path with a hidden component (such as `.ssh`, `.aws`, `.config`, `.env`), anything under `~/Library` and the Lateef state directory are refused. Setting `LATEEF_UPLOAD_ROOTS` (absolute directories separated by the platform path delimiter) narrows uploads to files inside those directories only. The `expectedOrigin` argument is supplied by the same agent, so it is a consistency check against navigation races, not user consent. Other files readable by your account remain attachable.
